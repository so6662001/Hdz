# 货袋子 · 找顺路车 / 悟运 · 发布运力 —— 高保真 HTML 原型与产品设计（v0.6）

> 场景：驾驶员在**悟运小程序**发布返程车、闲置车、顺路捎货信息；卖家、买家在**货袋子 PC 端、微信小程序、H5** 三端"找顺路车"，直接联系司机；找车方也可以**发布用车需求**，系统推荐匹配的顺路车、司机在悟运看到需求主动联系。这是一个**双方信息互动板块**：平台只做信息展示与真人真车核验，**不参与交易、不派单、不收运费、不做担保、不做承运人、不做网络货运平台**。
> 本目录是可交互的纯前端原型（无构建、无外部依赖、数据为模拟），并附产品设计说明与对三个关键问题的分析。它对应仓库中《物流板块介入路径分析》里的 **L1 运力撮合档**。

## 打开方式

```bash
cd prototypes/find-cheap-truck && python3 -m http.server 8080
# 访问 http://localhost:8080/
```

直接双击 `index.html` 也可以打开（总览页里的缩略预览使用 iframe，建议用本地静态服务器查看）。每个页面右上角有"设计说明"面板，顶部有原型导航条，均为原型辅助元素，不属于产品界面。

## 1. 定位与边界

| 项目 | 设计 |
| --- | --- |
| 供给 | 驾驶员（悟运存量司机为主）发布 **返程车 / 闲置车 / 顺路捎货** 三类运力信息 |
| 需求 | 货袋子卖家（送货）、买家（提货）在 PC / 小程序 / H5 找车 |
| 平台角色 | 信息服务方：核验真人真车、展示信息、提供联系与留痕、提供协议模板与保险入口、处置违规 |
| 平台不做 | 不签运输合同、不派单、不确认成交、不收运费、不代收代付、不开运输发票、不做担保赔付、不做纠纷调解与责任认定 |
| 为什么便宜 | 返程车与其空驶不如低价带货；司机直接对接货主，去掉信息部层层加价 |
| 为什么好用 | 车辆档案带钢材维度（鞍座、篷布、12m 长材、多点装卸），司机有装钢材经验与悟运履约记录 |
| 与既有规划的关系 | 《物流板块介入路径分析》L1 运力撮合。当货主明确要"有人负责、要发票"时升级到 L2（接入持牌网络货运平台合作承运） |

### 1.1 轻平台原则

目标是**只做双方信息互动，不做网络货运平台、不做承运人，但把信任问题解决掉**。判断标准：信任由系统自动完成的四件事解决 —— 真人真车核验、悟运真实履约数据、信息自动失效、联系留痕；任何需要人工持续投入或让平台介入交易的设计，都视为"做重"的信号。

| | 平台做 | 平台坚决不做 |
| --- | --- | --- |
| 信息 | 司机发运力、货主看运力、查看电话、联系结果反馈；信息按出发时间自动失效 | 不撮合成交、不派单、不确认成交、不做在线接单 |
| 钱 | 永远不经手 | 不收运费、不代收代付、不结算、不开运输发票、不收保费 |
| 身份 | 司机实名 + 人脸；车辆行驶证核验；一车一账号；复用悟运履约数据作为公开信用 | 不做证件分级（如"四证齐全"）、不做司机等级体系、不代替货主做尽调 |
| 工具 | 运输协议模板（双方自行签）、货运险入口（保险公司承保出单）、联系前风险提示 | 不做平台担保、不做先行赔付、不做纠纷调解与责任认定 |
| 人工 | 举报处置（恢复 / 下架 / 封号）、自动核验不一致的兜底复核、黑名单 | 不做运力监控大盘、不做规则开关面板、不做参考价人工校准、不做客服介入交易 |
| 出口 | 货主明确要"有人负责、要发票"时跳转合作的持牌网络货运平台（L2） | 货袋子自己不持牌、不承接 |

"轻"的量化验证：按当前数据量，一名兼职运营每周 3～4 小时即可维护整个板块；人工工时明显上升时先调规则，而不是加人加功能。

## 2. 命名

| 候选 | 评价 |
| --- | --- |
| **找顺路车**（已采用） | 一个词说清"为什么便宜"（车本来就要走这条路），不承诺价格、不像交易，符合"只做信息互动"的定位；与"找钢材"同构；副标题"返程车 · 闲置车 · 专装钢材"解释来源 |
| 找特价车（原方案，v0.3 弃用） | 价格钩子强，但"特价"像平台定价与促销，容易让人以为平台在卖运输服务，与不做承运人的定位不符；卡片保留"特价 -N%"市场价对比标签 |
| 回头车 | 行业口语，一听就懂；但覆盖不了闲置车。可作为"返程车"类目名 |
| 顺路钢运 | 强调钢材专用与顺路属性，品牌感强，价格钩子弱 |
| 捡漏车 / 省钱车 | 口语传播性好，适合活动与海报标题，不建议做正式功能名 |

## 3. 三端页面与关键交互

### 3.1 驾驶员端（悟运小程序）

| 页面 | 关键设计 |
| --- | --- |
| 我的运力（Tab） | ① 当前运单卡片"卸货后一键发返程"（把发布嵌进运单流程，是最主要入口）；② 每条运力显示浏览 / 来电 / 收藏与**自动下架倒计时**；③ 操作：已接单（选来源）、已出发（可转顺路捎货继续展示）、延长（出发时间同步顺延）、更多（修改 / 一键降价 / 分享 / 下架）；④ 发布满 24h 的"还闲着吗？"确认卡；⑤ 已结束列表显示终止原因，7 天内"再发一次" |
| 发布运力（`publish.html`） | 原则：**发布 = 一次点击或一句话，表单只是兜底**。① **一键发布**：页面预填好整张运力卡片（线路来自当前运单 / 上次发布 / 常跑线路 / 闲置模板；时间按卸货点推算；价格按司机默认策略"市场价 -15%"自动算；车辆用默认车；说明按车辆配置自动生成），点"一键发布"即发；卡片上可"改 / 换 / 改价"局部微调，不进表单；发布后卡片原地变"已发布"，可撤销、分享。② **语音发布**：按住说一句"明天早上从嘉兴回上海，17 米 5 的板有鞍座，30 块一吨"，识别后按规则解析出类型 / 出发地 / 目的地 / 时间 / 车辆 / 价格，识别到的打 ✓，缺的用 chips 一下补齐；原话直接作为"司机说明"展示给货主。③ **自动准备 / 自动发布**：运单卸货后弹通知一键确认；可进一步开"自动发布"（可撤销、可关）。④ 默认价格策略、只对认证企业展示电话等设置一次生效。原型中的语音识别与解析为规则模拟；实现时 ASR 用微信小程序同声传译插件或云厂商接口，解析可用规则 + 轻量 NLU |
| 手动填写（`publish-form.html`） | 兜底表单，3 步：选场景 → 线路时间（GPS 定位出发地、目的地多选 + 方向不限、快捷日期时段、展示期默认 = 出发时间窗结束）→ 车辆价格（车辆卡、市场参考区间 + 折扣快捷键 / 面议、短句拼接说明）→ 预览 → 成功页与微信卡片分享。也用于修改已发布信息 |
| 添加车辆 | 拍行驶证 OCR 自动填车牌 / 车型 / 核载 / 年份；车型图标网格、板长快捷；**装钢材配置**单独一节并标注"货主常筛"；常拉品种；3 张车辆照片（车头含车牌 / 板面 / 侧面）对外展示；证件仅核验不展示；一键生成车辆说明；核验不阻塞发布 |

### 3.2 找车端（货袋子 PC）

| 页面 | 关键设计 |
| --- | --- |
| 列表 | 主导航新增「找顺路车 NEW」；搜索条按找车人思维：车在哪 → 送到哪 → 时间 → 车型 → 货物，支持从现货订单带入线路；首屏信任 4 格；左侧筛选把钢材维度前置（鞍座 / 篷布 / 12m 长材 / 多点装卸 / 在途定位）并提供"可信度"筛选；卡片含线路、时间、可装吨位、车与装备、司机说明原话、资质徽章、好评与信息有效率、价格与市场参考对比；右侧：安全须知 + 协议模板 + 货运险报价、订阅线路（订阅数回传司机端）、小程序码、FAQ；底部"发布用车需求"（同样只是信息） |
| 详情 | 线路 / 时间 / 吨位 / 司机原话；车辆照片 + 参数 + 装钢材配置矩阵 + 车辆说明；司机履约（悟运运单）与找车用户评价；**信息状态轨迹**（发布时间与位置、核验项、被查看次数与最近反馈、自动下架时间）；右侧吸顶价格 + 查看电话 + 联系前确认 + 平台边界声明 |

### 3.3 找车端（货袋子微信小程序 / H5）

同一套页面用 `?shell=mp|h5` 切换两种壳：小程序壳有胶囊按钮与 Tab 栏；H5 壳有浏览器地址栏、"打开小程序"引导条和底部"订阅线路 / 打开小程序"操作条。H5 面向微信群 / 朋友圈分享、短信链接、PC 扫码场景，查看电话需手机号登录。

### 3.4 三端统一的"查看电话"流程

1. 需登录（企业认证用户优先；司机可设置"只对认证企业展示电话"）。
2. 强制阅读风险提示并勾选：平台不参与交易、不做担保；核人车证；签协议；投保；举报。
3. 显示号码，提示"本次查看已记录"，展示"已有 N 位货主查看"。
4. 联系结果反馈：已谈成 / 在沟通 / 未接通 / 车已被订走 / 信息不实 —— 反馈回流司机端并驱动信息真实性规则。

## 4. 运力信息状态机与终止机制

```
待核验 ──车辆核验通过──▶ 展示中 ──┬──▶ 已接单（司机点击 / 悟运派单自动标记）
                                 ├──▶ 已出发（司机点击；可转"顺路捎货"继续展示）
                                 ├──▶ 已到期（出发时间窗结束自动下架）
                                 ├──▶ 已下架（司机手动）
                                 └──▶ 待确认（展示满 24h）──未确认 2h──▶ 自动隐藏
任一终态 7 天内可「再发一次」→ 展示中
```

| 触发 | 机制 | 对找车方的影响 |
| --- | --- | --- |
| 到期自动下架 | 展示期默认 = 出发时间窗结束，可选 12 / 24 / 48h；到期前 2h 推送提醒，可一键延长（出发时间同步顺延）；累计延长超 48h 需再次确认 | 列表只显示未到期信息；详情显示倒计时 |
| 已接单 | 司机点击并选来源（货袋子 / 熟客 / 其他平台）；在悟运接到平台派单时系统自动标记 | 立即消失；已收藏用户收到通知 |
| 已出发 | 司机点击；空车出发仍想接货可改为"顺路捎货" | 同上 |
| 24 小时确认 | 闲置车 / 长有效期信息满 24h 弹"还闲着吗？"，未确认 2h 后自动隐藏 | 避免打到"早就有活"的车 |
| 反馈驱动 | "未接通"≥3 次提醒司机确认；"已被订走"≥2 次自动隐藏并通知司机；"信息不实"标记核实中、人工处理 | 反馈入口紧跟查看电话，成本极低 |
| 司机信用 | 信息有效率 = 有效联系 / 总联系；长期偏低者降权、限制发布数量 | 可按可信度筛选与排序 |

## 5. 信任与风控设计

| 层 | 做法 |
| --- | --- |
| 身份真实 | 只核"真人真车"：实名 + 人脸（第三方接口）；行驶证 OCR 与车牌照片一致；一车一账号。徽章只有两枚：实名 / 车辆认证，不做证件分级 |
| 信息真实 | 发布时 GPS 与出发地一致性校验（"定位一致"标签）；自动到期；24h 确认；反馈驱动隐藏；信息有效率 |
| 履约信用 | 复用悟运运单履约数据；找车用户联系后评价；投诉次数公示 |
| 联系留痕 | 查看电话需登录；记录时间与双方身份；司机可限制仅认证企业可见 |
| 风险前置 | 联系前强制阅读风险提示；详情页固定"联系前请确认"；运输协议模板；货运险入口（保险公司承保出单，平台不收保费、不做代理） |
| 事后处置 | 举报 → 核实中标记 → 处置只有三种：恢复 / 下架 / 封号（同步冻结悟运账号）；同一账号 30 天内 2 次下架自动升级封号；纠纷时向举报人提供联系记录（发布快照、查看电话时间戳、反馈、历史处置） |
| 平台边界 | 不签合同、不收运费、不派单、不开运输发票、不认定责任 → 不构成网络货运承运人；用户协议与页面声明反复明确 |

以上除"事后处置"外全部由系统自动完成，这是在不做承运人、不碰钱的前提下解决信任的核心：**信任来自核验、透明、留痕与工具，而不是平台介入交易。**

## 6. 三个问题的分析

### Q1 驾驶员会愿意上来发布吗？

**会，但不是为"一个新平台"上来，而是为"卸货后 10 秒多一条免费回程货线索"上来。** 司机现在找回程货靠微信群、信息部、满帮，多发一个地方的前提有四个：

1. **这里真有货主看。** 货袋子的买卖双方本身就是钢材运输需求方，而且是货主直接打电话，不经信息部转手 —— 这是司机最在意的"去中间层"。
2. **发布成本接近零。** 悟运运单到达卸货点即弹出预填好的返程车卡片，点一下就发；或按住说一句话语音发布；价格按默认策略自动算，不用查行情；愿意的话可开"自动发布"。
3. **免费、不抽佣、不收信息费。** 平台不做交易，天然成立。
4. **看得见反馈。** 曝光、来电、来电率与同线路对比；"这条线路有 12 家企业在等车"的订阅数；成功页"已推送给 N 位货主"。

冷启动策略：不靶向拉新司机，而是**从悟运存量司机与运单节点切入**，把发布变成运单流程里的顺手动作；同时用货主侧的"订阅线路"和"发布用车需求"把需求信号反向推给司机。主要风险是信息部 / 黄牛冒充司机批量发布，用一车一账号、定位一致、悟运履约和信息有效率来压制。

### Q2 找车方会不会担心有问题？

**一定会，而且这种担心是合理的** —— 一车钢材 10～15 万元，行业经典风险是骗货、放鸽子、坐地起价、货损。找车方真正在问三件事：

| 担心 | 产品回答 |
| --- | --- |
| 这个人是真的吗 | 实名人脸 + 行驶证核验 + 车辆照片（车头含车牌）+ 一车一账号 + 定位一致 + 悟运真实履约记录 → 比微信群里的陌生司机可信得多 |
| 这条信息还有效吗 | 自动到期倒计时、24h 确认、反馈驱动隐藏、信息有效率、状态轨迹公开 → 打过去基本有人接、车基本还在 |
| 出事有没有人管 | 联系留痕、举报处置、黑名单、提供联系记录；风险动作前置为"三件事"：核人车证、签协议模板、投货运险 |

找车方的担心**不能靠"平台担保"解决**（那会把货袋子变成承运人，触发网络货运许可、税务、承运人责任三重监管），而要靠"核验 + 透明 + 留痕 + 工具"把陌生交易的风险降到与熟车相当，并明确边界。

### Q3 万一车子出了问题怎么办？

先讲清法律与商业边界：平台不签运输合同、不收运费、不派单，就**不是承运人**；货损、事故、丢货的赔偿责任在司机 / 车队（《民法典》承运人责任），平台承担的是信息服务者的合理审核与协助义务。对应地：

- **事前**：核验准入；风险提示强制阅读；协议模板明确运费、时效、货损责任、回单；货运险一键入口（保险公司承保，平台不收保费不做代理，避免保险兼业代理资质问题）；装车时人车证核对指引，提货凭证只交给核对无误的车。
- **事中**：司机可授权开放在途定位（"车载定位"标识）；放鸽子 / 失联可在平台标记。
- **事后**：提供联系记录、发布信息、核验结果等凭证协助维权；举报核实后封号并联动悟运账号；严重者报案配合；案例沉淀为司机信用。
- **升级路径**：当货主明确要"有人负责、要发票"，进入 L2 —— 接入持牌网络货运平台做合作承运，由其承担承运人责任，货袋子仍不自持牌照。

**一句话：不承诺"平台赔"，承诺"平台核验、留痕、协助、处置"，并把保险和协议做成一键工具。**

## 7. 冷启动与运营建议

1. **供给先行但不铺开**：选 3～5 条货袋子现货订单最密集的线路（如上海 ⇄ 嘉兴 / 苏州 / 杭州），在悟运对常跑这些线路的司机开放发布并做运单节点提示。
2. **需求侧引流**：现货订单页 / 卖家中心增加"找顺路车"入口并带入线路；每周向订阅用户推送"本周顺路车"。
3. **信任标识不分级**：只有"实名 / 车辆认证"两枚徽章 + 悟运履约单数这一个数据标，让货主凭履约数据自己选，平台不做等级体系、不追求全员高门槛。
4. **反馈闭环优先于功能**：先把"查看电话 → 反馈"跑通，信息有效率是这个板块最重要的健康指标。
5. **关键指标**：在展运力数、线路覆盖、发布 → 来电转化率、信息有效率、找车方反馈"已谈成"数、举报率与处置时长、司机 7 日复发率。

硬处置（下架 / 封号）的必要配套。通知页一次讲清举报方、原因、系统佐证（悟运运单、多货主反馈、定位）、处置结果与 48 小时倒计时；申诉表单只有理由 chips、三类证据（聊天截图 / 通话记录 / 现场照片，至少 1 项）、一句话说明（可语音）；48 小时内出结果，期间处置维持。边界一致：平台只核实"信息是否属实、账号是否违规"，不裁定运费争议、不把证据转给对方、不代为协商。一次申诉核对约 5 分钟，纳入后台"举报处置"同一队列，不新增角色与视图。

### 9.3 合作承运分流页（`shipper/pc-l2.html`、`shipper/m-l2.html`）

轻平台的出口（既有规划 L2 档）。货主明确要 9% 运输发票、对公付款 / 月结、承运人对货损负责时，货袋子不自己做重，而是引导到合作的持牌网络货运平台。页面先让货主选需求再给建议（"都不需要"直接劝回直联司机），给出两条路对照表；关键差异化是 **"就用这台顺路车"**：货主已看中一台便宜的返程车只是缺发票，合作方把司机纳入其平台承运并开票，价格约 +8%～12%（税、险、服务费），司机不愿入驻则合作方改派同等车辆。每次跳转都有离开声明与勾选确认，承运关系明确在货主与合作方之间；货袋子只保留引导记录，收入为合作方推广费用，与货主运费无关。合作方资质（许可证号、承运人责任险额度）页面可查，货袋子按季度复核许可有效性。

### 9.4 语音解析校准工作台（`admin/asr-calibrate.html`）

产品 / 研发内部工具，不增加运营人工。样本来自司机在语音结果卡片上改过的字段（系统自动收集，等于司机免费标注）。两类修复：加词（地名简称"甬"、区域词"苏南"、车辆口语"高低板 / 前四后八"、方向词"回 / 哪都去"、价格口语"好说 / 一口价"）当场生效并可自动重跑同类样本验证；改规则（相对时间"卸完了 / 下半夜"、价格单位）记入研发待办。字段准确率指出短板（时间最弱，需结合运单状态推算）。目标：一次解析全对 ≥ 85%、平均补齐字段 ≤ 0.5，达到后每月看一次即可。实现建议：ASR 用微信小程序同声传译插件（支持方言），解析层规则 + 词典覆盖 90%，剩余交给轻量 NLU 或大模型抽取并回填同一套字段。

## 10. v0.3 用车需求：车找货的另一半

### 10.1 这样设计是否仍然"不做货运平台、不做承运人"

是。判断标准不是"有没有需求这个功能"，而是平台在需求上做了什么：

| 环节 | 用车需求里平台做的 | 不做的（做了就成货运平台） |
| --- | --- | --- |
| 发布 | 货主自填线路 / 时间 / 货物 / 需要的车 / 预算（选填），从货袋子订单带入 | 不代填运价、不审核价格、不要求"下单" |
| 匹配 | 按线路（同城 / 周边）→ 目的地（一致 / 方向不限 / 沿线可捎）→ 时间 → 装备 → 车型板长 → 吨位 → 司机履约打分，**推荐理由原样展示**（✓ 同城出发 / ✓ 有鞍座 / ! 只剩 12t 位） | 不派单、不指定司机、不"抢单"、不承诺"推荐即可用" |
| 联系 | 双向都是查看电话：货主看司机电话（既有流程）；司机看货主电话（对称：实名 + 车辆认证 → 风险提示 → 留痕 → 反馈）；v0.4 加"意向"：司机一键告诉货主"能接"，可选填参考价（以电话为准），货主决定先打给谁 | 没有报价榜、没有接单按钮、没有"选定司机"、没有平台确认成交 |
| 价格 | 只显示货主自填预算 + 市场参考区间 | 不定价、不抽成、不收信息费 |
| 结束 | 装车时间到自动下架 / 货主点已找到车 / 司机反馈"已找到车"≥2 自动隐藏 / 24h 未找到车确认 / 手动下架 | 不跟踪运输、不做回单、不做结算 |
| 通知 | D7（司机：沿线有新需求）、D8（司机：有意向的需求已找到车）、S5（货主：司机查看了您的电话）、S6（货主：匹配到车）、S7（货主：司机有意向）、S8（货主：装车顺利吗），均有频控 | 不推"平台已为您安排车辆"之类的话 |

红线：三端任何页面不出现"抢单 / 接单 / 报价榜 / 选定司机 / 平台确认成交 / 代收运费"字样；预算与参考价旁永远放"市场参考"而不是"平台指导价"，不显示"最低价 / 平均价"。

### 10.2 三端页面

- **PC `shipper/pc-need.html`**：入口在找顺路车列表下方与空态、hero 右侧。表单尽量不用填：从订单带入，选品种自动勾装备（热卷 → 鞍座；冷轧 → 篷布 + 鞍座；螺纹钢 / 型钢 → 12m 长材 + 绑带）。右侧**实时匹配**随填随变，完全匹配的在展车不用等发布，现在就能查看电话；部分匹配的折叠并标出缺项。发布成功页同时给两条路："N 台顺路车现在就能联系" + "N 位司机已收到您的需求"。**我的需求**：谁查看了我的电话（司机姓氏 + 车牌 + 悟运履约，接电话时可比对）、匹配车数、看匹配车 / 已找到车（问一下从哪找到的，只用于统计）/ 延长 / 下架 / 24h 确认 / 再发一次。
- **小程序 / H5 `shipper/m-need.html`**：三种填法（订单带入 / 按住说一句 / chips），语音规则解析与司机端同一套思路（地名别名、时间、品种、吨数、卷数、拼车、预算单位）；吸底的"N 台顺路车现在就匹配"点开是带匹配理由的车卡片，可直接查看电话；列表页第 1 条后插入发需求卡片，空态与 H5 底栏也给入口。
- **司机端 `driver/needs.html`**：默认 Tab「匹配我的运力」按司机展示中的每条运力分组，卡片上直接给匹配理由；「附近出发」按当前运单位置；「全部」给筛选 chips。需求卡片与运力卡片同构，多了货主认证与历史（发过 N 次需求、找到车 N 次）、"N 位司机已联系"（≥3 提示尽快打）。入口：运力 Tab 首页"沿线用车需求 N 条匹配您的运力"卡片、发布成功态"N 条用车需求匹配这条线"、服务通知 D7。订阅常跑线路的需求通知有频控；底部给反向入口"发一条运力让货主来找您"。

### 10.3 闲置车单独发布（`driver/publish-idle.html`）

闲置车与返程车的差别在于**没有确定线路和时间**，原先只作为一键发布的第 4 张模板卡和手动表单的一个场景，字段与返程车共用，不够直白。现在单独一页：车在哪（定位）/ 闲到什么时候（今天 · 明天 · 3 天 · 一周 · 长期）/ 想去哪（方向不限 · 300km · 150km 短驳 · 选几个方向）/ 接什么活（整车长途 · 市内短驳 · 拼车 · 可等一两天）/ 价格（默认面议，也可按吨 / 车 / 公里）/ 用哪台车，全部 chips 按定位与常跑习惯预填，一键发布或按住说一句。维护规则：到期自动下架；**长期闲置每天早 8 点问一次"还闲着吗"**（D3），未确认自动隐藏；悟运派单自动下架；货主反馈"已被订走"≥2 隐藏。卡片下方直接列出这台车现在就能接的附近用车需求（`H.matchNeeds`，方向不限的匹配范围天然大）。三种运力类型在发布页顶部切换：返程车（`publish.html`）、闲置车（本页）、顺路捎货（`publish-form.html?kind=share`）。

### 10.4 匹配规则（`shared/common.js` `H.matchPosts / H.matchNeeds`）

出发地同城 +40 / 周边（≤100km 城市表）+15，否则不推荐；目的地一致 +30 / 方向不限 +20 / 沿线可捎 +20 / 不同 −40；时间吻合 +15 / 不吻合 −10；每项所需装备 有 +10 / 无 −25；车型 +5、板长 +5；可装吨位够 +10 / 不够 −30；司机好评、车辆认证、悟运单数小幅加分。总分 < 50 不展示；无缺项为"完全匹配"，有缺项为"部分匹配"并列出缺项。规则透明、可解释、无人工干预，与"不做重"一致；上线后仅按"货主点了哪些匹配车 / 司机打了哪些需求"调权重。

### 10.5 v0.4 意向 + 先打给谁 + 联系结果反馈（替代"司机报价 → 商家选一个 → 完成互评"）

**为什么不照搬竞价链路。** 竞价（司机报价、商家选一个、双方联系、完成后互评）在这个场景有四个问题：

| 环节 | 问题 |
| --- | --- |
| 司机报价 | 钢材用车的价格取决于装卸等待、是否要吊车、回单、结算周期，报价框里写不清、电话两句就清楚；多司机盯一条需求报价必然互相压价，而顺路车司机是这个板块最稀缺的供给 |
| 商家"选一个" | 平台一旦记录"货主选了张师傅"就是平台确认成交，爽约 / 放空 / 货损的责任第一反应都是"平台上选的，平台管" |
| 电话 / 微信联系 | 本来就是这样设计的，没问题 |
| 完成后互评 | 互评前提是平台知道"完成"了，又要一层确认；钢材圈子小，双向评分很快被"给差评就不合作"架空 |

**但竞价想解决的两个痛点是真的。** 一是货主拿到推荐名单后不知道谁有意向，要挨个打，打三个没接就放弃；二是司机打完没谈成，其他司机不知道，结果没有闭环，大家空等。

**综合方案（已落到原型）：**

```
货主发需求 ─→ 系统推荐 + 推送区域内匹配司机（v0.3）
                 │
司机看到 ─→ 一键「有意向」（可选填参考价，标注"以电话为准"，可带一句话）
                 │      · 不排序、不比价、不锁定；货主看不到别人的价；司机随时可直接打电话
                 │      · 24 小时未联系自动过期；一条需求最多 5 位，达到后停止推送、卡片显示"意向已满，可直接打"
货主「我的需求」 ─→ "N 位司机有意向"（姓氏 + 车牌 + 悟运履约 + 参考价 + 一句话）
                 │      · 「先打给他」只是联系顺序，不是"选定"；平台不记录成交
双方电话谈定 ─→ 货主点「已找到车」（可选勾是哪位司机，也可不勾）
                 │      · 其余有意向的司机收到 D8「该需求已找到车」，不再空等；平台不据此确认成交
                 └→ 联系结果反馈（替代互评）
                        货主侧：如约到车 / 在沟通 / 没谈成 / 司机爽约 / 坐地起价 / 信息不实
                        司机侧：如约装车 / 在沟通 / 没谈成 / 货主已找到车 / 货主放空 / 电话里压价 / 信息不实
                        · 只在真实联系过的双方之间；结构化选项不是打分；不公开；无需平台判定"完成"
                        · 负面项累计进入现有核验 / 黑名单（同一司机 2 次爽约暂停展示；同一货主 2 次放空限制发布）
```

三个细节：意向人数达 5 时提示货主"建议尽快联系"并停止推送，避免一条需求把周边司机全叫来；微信在电话之后由双方自行加，平台不做微信名片交换，否则留痕、风险提示、黑名单全部被绕过；参考价旁只放"市场参考 ¥xx–xx/吨"，不放"最低报价 / 平均报价"，防止事实上形成平台指导价。

实现：`shared/data.js` `INTENTS / INTENT_COUNT / INTENT_CAP / FEEDBACK`；`shared/common.js` `H.intentSheet`（司机端弹层）、`H.intentList / H.intentRow`（货主端列表）、`H.foundDialog`（已找到车 · 可勾司机 · 通知其余）、`H.fbChips / H.bindFb`（双向结构化反馈，替换了原来的"已谈成 / 未接通"chips）；`driver/needs.html` 卡片与详情的「有意向」、顶部"您对 N 条需求有意向"条；`shipper/pc-need.html`、`shipper/m-need.html` 我的需求侧栏 / 卡内"有意向的司机"、「先打给他」、已找到车、已结束记录下的反馈；`driver/notify.html` D8 / S7 / S8。

### 10.6 v0.5 线路选址：不用手打地址（`H.addrPicker / H.addrQuick`）

录入需求时地址是最烦的一步，尤其"送到我自己公司"这种每次都一样的。现在提货地 / 送货地两个字段：

- **字段下方快捷 chips**：「送到我司 / 在我司装」一键带入认证的公司地址（`HDZ.MY_COMPANY`，司机端会看到公司名与收货时间，减少"送哪儿"的电话）；小程序多一个「◎ 当前位置」（人在仓库现场发需求时直接用）；前两个常用仓库；「地图选点 / 更多」。
- **选址弹层**（PC 弹窗 / 小程序底部弹层）：顶部搜索（地址簿 + 各城市仓库 / 市场 / 工地 + 城市名）；我司位置大卡；常用地址按使用次数、最近用过；城市切换 + **示意地图**——点一下，7 个单位内有仓库 / 市场就吸附到它，否则记为"××区 · 地图选点（东南部，联系时报具体路名）"。选中的地址始终显示在搜索框下方，确认后回填城市 + 详细地址。
- **来源标签**：字段旁显示 我司位置 / 订单地址 / 常用地址 / 最近用过 / 当前位置 / 地图选点，手改文字后标签消失；订单带入时送货地若是公司地址自动标"我司位置"。
- 地图坐标（`fromLoc / toLoc`）随需求保存，后续可用于按距离推荐与司机端导航，但匹配打分仍只用城市，保持规则简单可解释。地图为示意图（`HDZ.MAP`），真实实现接腾讯 / 高德小程序地图组件即可。

### 10.7 v0.6 分享到微信群：接收形态与完整闭环（`H.shareSheet` / `driver/need-landing.html`）

"分享到微信群"原来只是一个 toast。真实约束是：**微信小程序卡片只能分享本小程序的页面**——货主在货袋子里生成的卡片，司机点开进的是货袋子，不是悟运；反过来司机分享运力给货主也一样。所以跨小程序的分享只有一条路：**海报图片 + 对方小程序的小程序码**（`getUnlimited`，scene 带 `需求ID_分享人`），配一段群文案。原型把这条路完整画出来：

- **分享弹层**（PC 弹窗 / 小程序底部弹层，货主端「我的需求」→「分享到司机群」，司机端「我的运力」→ 更多 → 分享、发布成功卡片 → 分享）：三个目标——发到司机群（海报 + 悟运码，默认）/ 发给同事（货袋子小程序卡片，只用于同事一起盯需求、帮打电话）/ H5 链接（司机没装悟运也能先看内容，看电话时引导注册）。右侧 / 下方是"**对方在群里看到的**"微信群聊预览（海报图 + 文案 + 一位司机回复）和"**怎么形成闭环**"四步；底部"复制群文案 / 保存海报 · 发到微信群"。海报上**没有电话**，电话只在认证后的小程序里看并留痕；文案里也不放电话。
- **司机扫码落地页**（`driver/need-landing.html?state=new|ok|ended`）：顶部"张经理（上海某钢贸）通过微信群分享给您"既是信任线索也是归因标记。三种状态必须都处理：**未注册**——需求内容、市场参考、货主认证状态都能看（让司机觉得值得注册），电话与「有意向」被挡，三步（微信手机号一键注册 → 实名 + 人脸 → 拍行驶证加车，约 3 分钟）在本页完成后自动回到这条需求，也可"先看看，稍后再说"存到注册后的沿线需求；**已认证**——与沿线需求卡片同一套「有意向」/「查看货主电话」；**需求已结束**——海报可能还在群里传，扫进来看到"已找到车"、电话不再显示，顺手给附近 / 沿线其他需求与"发一条运力"入口。
- **分享归因统计**（`HDZ.SHARE_STATS`）：货主「我的需求」/ 司机「我的运力」卡片下显示"09:08 发到 2 个群 · 被打开 12 次 · 2 位司机查看电话来自分享 · 1 位有意向 · 新注册 1 人"。只做展示，**不分成、不奖励现金**，司机侧除"谁分享的"外不显示任何分享数据。
- 闭环四步：① 货主保存海报 / 复制文案发到司机群（可多个群）→ ② 司机长按识别悟运码进落地页（未注册先注册认证）→ ③ 司机打电话 / 点「有意向」，货主在「我的需求」看到并标注"来自群分享"→ ④ 谈定点「已找到车」，群里那张海报的码再扫就是"已找到车 + 附近其他需求"，不会再有人打给货主。司机分享运力到货主群对称：海报 + 货袋子码 → 运力详情（手机号登录 → 风险提示 → 看电话留痕）→ 已接单 / 已出发后码失效为"该车已有活 + 同线路其他车"。
