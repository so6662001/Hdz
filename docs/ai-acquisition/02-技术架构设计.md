**设计原则**

1. **编排在服务端，操作在执行端**：服务端不持有任何个人微信/抖音/小红书登录态，只下发"做什么"，执行端在真机 App 里"怎么做"。账号风险与服务端隔离，出问题只影响单台设备。
2. **渠道可插拔**：所有渠道经 `ChannelAdapter` SPI，触达/跟进/海报分发引擎不感知渠道差异；新增渠道只加适配器。
3. **规则优先，AI 兜底，人工把关**：意图识别、回复匹配都先走可解释规则；LLM 只在规则未命中时介入并记录置信度；报价/合同/承诺强制人工。
4. **一切可回放**：抓取原文、渲染后消息、执行端回执与截图、匹配理由、任务运行日志全部落库，便于排错与合规举证。
5. **复用而非重建**：模型网关、企业资料库、海报渠道码、企微通知、线索中心均复用平台已有能力。

## 3. 渠道抽象层 ChannelGateway

### 3.1 SPI 定义

```java
public interface ChannelAdapter {
    Platform platform();                 // WECOM / WECHAT_PERSONAL / DOUYIN / XIAOHONGSHU / FORUM / HDZ_INTERNAL
    Set<Capability> capabilities();      // CAPTURE_COMMENTS, CAPTURE_GROUP, CAPTURE_MOMENTS, SEND_DM,
                                         // REPLY_GROUP, POST_MOMENT, PUBLISH_POST, PULL_INBOX
    ExecMode execMode();                 // API / HTTP / RPA（决定是同步调用还是下发执行端）

    CaptureResult capture(ChannelAccount acct, CaptureRequest req);          // 抓取评论/话题/群/朋友圈
    SendResult    sendMessage(ChannelAccount acct, DirectMessage msg);       // 私聊/私信
    SendResult    replyInGroup(ChannelAccount acct, GroupReply reply);       // 群内回复
    PublishResult postMoment(ChannelAccount acct, MomentPost post);          // 朋友圈（图+文）
    PublishResult publishPost(ChannelAccount acct, ContentPost post);        // 小红书笔记 / 论坛帖
    List<InboundMessage> pullInbox(ChannelAccount acct, Cursor since);       // 拉取入站（无回调渠道用）
    HealthStatus  health(ChannelAccount acct);                               // 在线/风控/需验证/封禁
}
```

- `execMode = RPA` 的适配器不直接操作，而是把请求编码为**执行端指令**交给 `ExecutorGateway`，异步等待回执（`CompletableFuture` + 回执回调，超时默认 120 s）。
- 触达/跟进引擎只依赖 `ChannelRegistry.get(platform).sendMessage(...)`，不感知 API 与 RPA 差异。
- 每个渠道账号有 `capabilities` 的运行时子集（例如企微账号不支持"抓他人评论区"），任务创建时即校验。

### 3.2 渠道能力矩阵（一期 / 二期）

| 能力 | 企业微信（API） | 个人微信（RPA） | 抖音 | 小红书 | 行业论坛（HTTP/浏览器） | 货袋子站内（内部） |
|------|:--:|:--:|:--:|:--:|:--:|:--:|
| 抓评论区/话题页 | — | — | 二期 RPA（自家内容一期） | 二期 RPA（自家笔记一期） | 一期 | 一期（圈子评论/询价） |
| 抓群消息/成员 | 一期（客户群 API） | 二期 RPA | — | — | — | — |
| 抓朋友圈 | 一期（客户朋友圈互动） | 二期 RPA | — | — | — | — |
| 私聊/私信 | 一期（客户联系 API，需先为客户） | 二期 RPA | 二期 RPA（回复评论者私信受限） | 二期 RPA | 一期（站内信/回帖） | 一期（站内消息） |
| 群内回复 | 一期 | 二期 RPA | — | — | — | — |

## 4. 执行端（Executor）设计

### 4.1 形态

- **获客助手 App（Android）**：安装在商家的工作手机或租用的云手机上，基于无障碍服务（AccessibilityService）读取界面树、模拟点击/输入/滑动；不 root、不 hook 微信进程，与真人操作路径一致。
- 一台设备 = 一个执行端 = 同时只登录一个微信号（抖音/小红书可同机）。
- 设备通过扫码绑定到商家，与服务端保持 WebSocket 长连接（心跳 30 s），断线自动重连；离线时其任务在队列中等待或按策略改派同商家其他在线设备（仅限同账号才能改派，因此实际上是等待）。

### 4.2 指令协议（JSON over WebSocket）

```jsonc
// 服务端 → 执行端
{
  "cmdId": "c_01J8...",           // 幂等键
  "type": "SEND_DM",              // CAPTURE_COMMENTS | CAPTURE_GROUP | CAPTURE_MOMENTS | SEND_DM |
                                  // REPLY_GROUP | POST_MOMENT | PUBLISH_POST | PULL_INBOX | HEALTH_CHECK
  "platform": "WECHAT_PERSONAL",
  "accountId": 1023,
  "payload": {
    "peer": { "nickname": "张总", "remark": "", "wxidHint": null },
    "text": "张总，看到您在XX论坛问企业内训的事……",
    "attachments": [{ "type": "IMAGE", "url": "https://oss/.../poster-Q7K2MV-G.png" }]
  },
  "pacing": { "preDelayMs": 4200, "typingSpeedCps": 6, "postDelayMs": 1800 },   // 由风控中心计算
  "deadlineAt": 1758790000000,
  "evidence": "SCREENSHOT_ON_FINISH"   // NONE | SCREENSHOT_ON_FINISH | SCREENSHOT_ON_ERROR
}

// 执行端 → 服务端（回执）
{
  "cmdId": "c_01J8...",
  "status": "OK",                 // OK | FAILED | BLOCKED | NEED_VERIFY | NOT_FOUND | TIMEOUT
  "code": "",                     // 例如 WX_FREQ_LIMIT / WX_NOT_FRIEND / UI_CHANGED
  "message": "",
  "data": { "sentAt": 1758789990000, "items": [ /* 抓取类指令返回的记录 */ ] },
  "screenshotUrl": "https://oss/.../c_01J8.png",
  "deviceState": { "battery": 78, "foregroundApp": "com.tencent.mm", "wxVersion": "8.0.xx" }
}

// 执行端 → 服务端（主动事件）
{ "event": "INBOUND_MESSAGE", "accountId": 1023, "peer": {...}, "text": "多少钱一吨？", "receivedAt": ... }
{ "event": "HEARTBEAT", "deviceId": "...", "accounts": [...], "health": "ONLINE" }
{ "event": "RISK_SIGNAL", "accountId": 1023, "signal": "CAPTCHA_SHOWN" }
```

- **幂等**：`cmdId` 为幂等键，执行端本地持久化已执行 cmdId，重连重发不重复发送。
- **拟人化参数由服务端下发**（`pacing`），执行端只执行；便于统一调参与审计。
- **证据**：发送类指令完成后截图上传 OSS，回执携带 URL；争议时可回溯。
- 执行端 UI 适配（微信版本升级导致控件变化）是长期维护成本，`UI_CHANGED` 回执触发告警并自动暂停该平台指令。

## 5. AI 服务层

统一经 `AiFacade` 调用海报系统的 `ModelGateway`（多厂商路由、重试、计费、缓存）。**所有 LLM 调用都记录 prompt 摘要、模型、耗时、费用、输出**（`hdz_acq_ai_call_log`）。

| 组件 | 输入 | 输出 | 策略 |
|------|------|------|------|
| `IntentClassifier` | 抓取原文（批量 ≤20 条）、商家品类、意图短语 | `intent`（INQUIRY/ASK_PRICE/ASK_MATERIAL/ASK_RECOMMEND/SIGNUP/IRRELEVANT）、`score` 0~100、`reason` | 先关键词/正则；命中直接给分（关键词权重），未命中才调 LLM；同 hash 结果缓存 7 天 |
| `MessagePersonalizer` | 话术要点、变量（昵称/来源/历史互动/产品）、语气、长度限制 | 一条消息文本 | 仅当话术 `ai_polish=true`；输出再过 `PersonalizationValidator`（必须包含昵称或来源要素）与内容安全；失败回退模板渲染 |
| `ReplyClassifier` | 客户回复 + 最近 3 轮上下文 + 话术分类列表 | `category`、`confidence`、`entities`（数量/规格/交期/地址） | 仅规则未命中时调用；confidence <0.7 转人工；抽到 entities 触发高意向判定 |
| `NlTaskParser` | 自然语言任务描述 + 商家可用渠道/话术/字段 | `JobSpec` JSON（见 5.1） | Function-calling / JSON Schema 约束输出；`JobSpecValidator` 校验后生成确认卡片，用户确认才保存 |
| `Moderation` | 出站文本 | pass / reasons | 内容安全 API + 广告法禁用词库（"最低价""第一"等）+ 商家自定义禁词 |

### 5.1 JobSpec（自然语言任务的结构化结果）

```jsonc
{
  "name": "每日抓取线索",
  "action": "CAPTURE",                       // CAPTURE | OUTREACH | FOLLOW_UP | REFRESH_DASHBOARD | POSTER_DISPATCH | CUSTOM
  "schedule": { "cron": "0 0 9 * * ?", "timezone": "Asia/Shanghai", "humanText": "每天 09:00" },
  "params": {
    "platforms": ["DOUYIN", "XIAOHONGSHU", "FORUM"],
    "captureRuleIds": [1, 2],
    "filter": { "stage": ["NEW"], "minScore": 60, "createdWithinDays": 3 },   // OUTREACH / FOLLOW_UP 用
    "scriptId": 12,
    "channelAccountIds": [1023],
    "maxCount": 200,
    "dryRun": false
  },
  "guardrails": { "requireApproval": false, "notifyOnFinish": ["owner"] },
  "parseTrace": { "model": "qwen3.5", "confidence": 0.92, "ambiguities": ["未指定渠道，默认全部已绑定渠道"] }
}
```

用户在确认卡片上可直接修改任何字段；保存后 `humanText` 与原始自然语言一同存档，"改了指令后重跑"即修改 NL → 重新解析 → 重新确认。

## 5A. 跟进流程引擎 FlowEngine（分支任务编排）

### 5A.1 为什么要两层

```
被动层  ReplyMatcher / ConversationEngine：客户说话 → 关键词/LLM → 立即回话术     秒级、反应式
主动层  FlowEngine：线索进入流程 → 按 DAG 推进 → 在 Wait 类节点停下等事件/定时     天级、编排式
```

线性链（话术 `follow_up_after_hours → follow_up_script_id`）只能表达"A 之后 N 小时发 B"。真实 SOP 是分叉的：3 天未回复发案例、回复问价转人工、说再考虑 7 天后发活动、期间扫了海报码立即唤醒、高意向 24 小时未处理升级主管。流程引擎把这些显式化为一张图，一条线索"当前在第几步、下一步何时"随时可见。

**两层边界**：`WaitForReply` 节点带开关 `autoReplyByScriptLib`（默认 true）。开启时被动层照常秒回，流程只消费这次回复的**类别/实体**做分支，不重复发送；关闭时由流程节点决定发什么（用于报价等需要收口的场景）。

### 5A.2 节点集（一期）

| 节点 | 配置 | 出口 |
|------|------|------|
| `Trigger` | `on`: STAGE_ENTER / MANUAL / CAPTURED / POSTER_SCANNED；条件：stage、minScore、platforms、tags；`priority`（抢占用） | 单出口 |
| `Send` | `scriptId`、`channelAccountId?`（默认线索所在账号）、`aiPolish?` | 单出口；发送失败走 `onFail`（默认 End(handoff)） |
| `Wait` | `hours` 或 `until`(HH:mm，落到活跃时段内) | 单出口 |
| `WaitForReply` | `timeoutHours`、`autoReplyByScriptLib` | `NO_REPLY` / `REFUSED` / 回复类别（`ASK_PRICE`、`ASK_CASE`、`CONSIDERING`、…来自话术分类）/ `HAS_ENTITIES` / `OTHER`(`*`) |
| `Branch` | 条件表达式：stage、intentScore、platform、tags、outreachCount、scannedPoster、clickedLink（二期）、hoursSinceLastActive | 多出口 + `default` |
| `HumanTask` | `kind`: FOLLOW_UP / QUOTE / CONTRACT / CUSTOM；`assignee`（owner/指定人）；`escalateAfterHours` | `DONE` / `ESCALATED` |
| `SetStage` / `Tag` / `Notify` | 目标阶段 / 增删标签 / 通知对象与模板 | 单出口 |
| `GoTo` | `target`、`maxLoops`、`onExceed` | 单出口 |
| `End` | `stage?`（SILENT/LOST）、`reason?`、`handoff`（交给人工） | 终止 |

二期扩展：`ClickedLink`/`OpenedPoster` 事件分支、`ABSplit`（随机分流做话术 A/B）、`SubFlow`、多流程并行。

### 5A.3 定义示例（JSON DAG）

```jsonc
{
  "name": "首触-标准跟进 SOP", "version": 2,
  "trigger": { "on": "STAGE_ENTER", "stage": "NEW", "minScore": 60, "priority": 10 },
  "guardrails": { "maxAutoSends": 4, "maxLoops": 2 },
  "nodes": {
    "n1": { "type": "Send", "scriptId": 101, "next": "n2" },
    "n2": { "type": "WaitForReply", "timeoutHours": 72, "autoReplyByScriptLib": true,
            "branches": { "NO_REPLY": "n3", "REFUSED": "end_lost", "ASK_PRICE": "n5",
                          "CONSIDERING": "n4", "HAS_ENTITIES": "n6", "*": "n2b" } },
    "n3": { "type": "Send", "scriptId": 102, "next": "n3w" },
    "n3w":{ "type": "WaitForReply", "timeoutHours": 72, "branches": { "NO_REPLY": "end_silent", "*": "n2b" } },
    "n4": { "type": "Wait", "hours": 168, "next": "n7" },
    "n5": { "type": "HumanTask", "kind": "QUOTE", "escalateAfterHours": 2, "next": "n2b" },
    "n6": { "type": "SetStage", "stage": "HOT", "next": "n8" },
    "n7": { "type": "Send", "scriptId": 105, "next": "n3w" },
    "n8": { "type": "Notify", "to": "owner", "next": "end_human" },
    "n2b":{ "type": "GoTo", "target": "n2", "maxLoops": 2, "onExceed": "end_human" },
    "end_silent": { "type": "End", "stage": "SILENT" },
    "end_lost":   { "type": "End", "stage": "LOST", "reason": "REFUSED" },
    "end_human":  { "type": "End", "handoff": true }
  }
}
```

同一段流程可由自然语言生成："首触后 3 天没回复发案例，再 3 天没回复就静默；问价转人工；说再考虑 7 天后发活动"→ `NlTaskParser` 输出 DAG → 确认卡片（纵向树预览）→ 保存。

### 5A.4 运行模型

```
进入：LeadStageMachine / 抓取 / 手动 / 扫码 → FlowEventListener 匹配 Trigger
   → 同商家同线索仅一个 ACTIVE 实例；新流程 priority 更高则抢占（旧实例 PREEMPTED）
   → 创建 flow_instance(def_version 固定, current_node=first, ctx={})

推进（FlowEngine.advance(instance)）：
   loop:
     node = def.nodes[current]
     执行节点 → 若为 Wait / WaitForReply / HumanTask：
         写 follow_up(flow_instance_id, node_id, due_at=timeout, status=PENDING) 作为定时器
         instance.status=WAITING, 返回
     否则取出口 next，current=next，记 flow_step_log；命中 End → COMPLETED

唤醒：
   · 定时器：FollowUpScheduler 扫 due_at≤now 的 follow_up → advance(instance, event=TIMEOUT)
   · 事件：入站消息(带 ReplyMatcher 的类别/实体) / 扫码 / 阶段变化 / HumanTask 完成
        → 找 WAITING 实例 → 取消其定时器 follow_up(SKIPPED) → advance(instance, event)
   · 幂等：instance 行级锁 + step_seq 递增；同一事件重复投递只推进一次
```

### 5A.5 护栏（流程再复杂也不能越过）

- 黑名单 / 拒绝词 → 该线索所有实例立即 TERMINATED，不再执行任何 `Send`。
- `Send` 仍经 渲染 → 个性化校验 → Moderation → RiskGuard 节流；不满足则该步失败走 `onFail`。
- 单实例累计自动发送 ≤ `guardrails.maxAutoSends`（默认 4，且 ≤ 风控 `max_outreach_per_lead`）；`GoTo` 有 `maxLoops` 硬上限。
- 实例绑定进入时的定义版本；发布新版本只影响新进入的线索，在途实例可由管理员选择"迁移到新版本"（仅当当前节点 id 在新版本仍存在）。
- 人工接管会话（HUMAN 状态）时，实例自动 PAUSED，交还机器后 RESUMED。
- 定义保存时静态校验：无孤立节点、所有出口可达 End、`GoTo` 目标存在、脚本/账号存在、分支键属于合法类别集。

## 6. 核心时序

### 6.1 抓取（RPA 渠道）

```
XXL-Job(09:00) → CaptureScheduler.run(merchant)
  → 遍历启用的 CaptureRule → ChannelRegistry.get(platform).capture()
     → RpaAdapter 生成 CAPTURE_COMMENTS 指令 → ExecutorGateway.dispatch(accountId, cmd)
        → 执行端：搜索关键词 → 打开内容 → 滚动读评论（≤ N 页）→ 回执 items[]
     → CaptureIngestService.ingest(items)
        → raw_hash 去重 → 写 capture_raw
        → IntentClassifier.classify(batch) → 更新 raw.intent/score
        → score ≥ 阈值 → LeadDedupService.find(platform, platformUserId) → 新建/合并 lead
        → LeadAssignService.assign(lead) → lead_event(CAPTURED/RECAPTURED)
        → score ≥ 80 → 企微通知 owner
  → job_run 记录（抓取数/去重数/建线索数/失败数），SSE 推送进度
```

### 6.2 触达

```
XXL-Job(10:00) 或 手动 → OutreachEngine.run(jobSpec)
  → LeadService.query(filter) → 排除黑名单/静默/已触达
  → for lead: ScriptService.pickFirstTouch(lead) → TemplateRenderer.render(script, vars)
       → PersonalizationValidator.check()   ✗ → 任务 FAIL(缺少变量: nickname)，dryRun 时前端直接展示
       → (ai_polish) MessagePersonalizer → Moderation
       → 写 outreach(QUEUED) → SendQueueService.enqueue(accountId, outreachId)
  → SendWorker(每账号单线程) 循环：
       RiskGuard.acquire(account) （令牌桶+活跃时段+养号曲线；不满足则等待）
       → 计算 pacing（随机延迟）→ adapter.sendMessage()
       → API 渠道同步返回 / RPA 渠道等待回执
       → 更新 outreach(SENT/FAILED/BLOCKED) → lead.stage=CONTACTED → lead_event
       → BLOCKED/NEED_VERIFY → CircuitBreaker.trip(account) → 告警 → 该账号队列暂停
```

### 6.3 入站回复处理

```
执行端 INBOUND_MESSAGE / 企微回调 / 论坛轮询 → InboundRouter.route(msg)
  → 定位 conversation（platform+accountId+peerId）→ 关联 lead（无则按昵称匹配，仍无则创建"未知来访"线索）
  → 写 message(IN) → outreach.replied=1 → lead.stage≥REPLIED → RealtimeCounter.incr(reply)
  → ConversationEngine.handle(conversation, msg)
       ① BlacklistService.isRefusal(text) → 拉黑 + LOST + 结束
       ② ScriptMatcher.matchByRules(text) → script
       ③ 未命中 → ReplyClassifier(LLM) → category → ScriptService.pick(category)
       ④ 仍未命中 → EscalationService.toHuman(conversation, reason=NO_MATCH)
       → script.requiresHuman → 发过渡话术 + ApprovalService.create(QUOTE/CONTRACT/PROMISE)
       → 否则 走 6.2 的渲染→校验→节流→发送链路（direction=OUT, auto=1）
           （若线索有 WAITING 于 WaitForReply 且 autoReplyByScriptLib=false 的流程实例，则跳过被动回复）
       → 发布事件 ReplyClassified(lead, category, entities) → FlowEventListener（见 6.8）
       → 无活动流程实例时：script.followUpAfter → FollowUpService.schedule(lead, due)（简易链兼容）
       → 高意向判定（score/entities）→ HOT → 企微通知
```

### 6.4 跟进未回复（14:00）

```
XXL-Job → FollowUpScheduler.run(merchant)
  → follow_up where status=PENDING and due_at<=now
  ├─ flow_instance_id 非空（流程定时器）→ FlowEngine.advance(instance, TIMEOUT) （见 6.8）
  └─ 简易链跟进（无流程）：
       校验 lead 仍处于 CONTACTED/REPLIED 且最近无入站
       → 累计自动跟进次数 ≥ maxAutoFollowUps(默认2) → lead.stage=SILENT，follow_up=SKIPPED
       → 否则 选二次跟进话术 → 走触达链路 → follow_up=DONE，记 lead_event(FOLLOW_UP_SENT)
```

### 6.5 海报分发

```
用户建海报分发任务(posterSessionId, targets[], scheduleAt)
  → for target.channel in {群, 朋友圈, 小红书, 论坛}:
       调海报系统 POST /posters/sessions/{id}/shares {channel: group|moments|other}
         → 返回 track_code + 按渠道码重绘二维码的 image_url
       → 写 poster_dispatch_item(target, trackCode, imageUrl, status=QUEUED)
  → 到时后按渠道账号入队 → RiskGuard → adapter.postMoment / replyInGroup(图片) / publishPost
  → 回执更新 item 状态 + 截图
  → 扫码发生时海报系统 /q/{code} 写 poster_scan / poster_lead → 事件推送本模块 → 创建/合并线索（来源=海报-渠道）
```

### 6.6 自然语言任务创建

```
用户输入 "每天下午2点跟进未回复客户" → POST /jobs/parse
  → NlTaskParser（携带商家上下文：可用渠道、话术、字段）→ JobSpec + ambiguities
  → JobSpecValidator（cron 合法、渠道存在、话术存在、maxCount ≤ 风控上限）
  → 返回确认卡片数据 → 用户修改/确认 → POST /jobs 保存 → 注册 XXL-Job（或 Quartz）
  → 「试运行」= dryRun=true 立即执行一次：只渲染不发送，返回前 N 条预览与校验结果
```

### 6.7 看板刷新（17:00 + 实时）

```
XXL-Job(17:00) → StatAggregator.aggregate(merchant, today)
  → 按 (merchant, owner, platform) 聚合：captured / leads_new / outreach_sent / replied / hot / won / lost / auto_replies / human_handled
  → upsert stat_daily
看板查询 = stat_daily(历史) ⊕ RealtimeCounter(Redis 当日计数) ⊕ 实时列表（待跟进/待人工/HOT）
```

### 6.8 跟进流程实例推进

```
线索进入 NEW（抓取/导入）→ 事件 StageEntered
  → FlowEventListener：匹配启用流程的 Trigger（stage/minScore/platform）→ 已有 ACTIVE 实例？
       ├─ 无 → 创建 flow_instance(version=当前发布版, node=n1)
       └─ 有 → 新流程 priority 更高则旧实例 PREEMPTED，否则忽略
  → FlowEngine.advance(instance)
       n1 Send → 走触达链路（QUEUED，发送结果异步）→ 记 step_log → next n2
       n2 WaitForReply → 写 follow_up(flow_instance_id, node=n2, due=now+72h) → instance WAITING

客户 30h 后回复"多少钱一吨"
  → 6.3 被动层：命中价格话术 → requires_human → 过渡语 + 审核单
  → 事件 ReplyClassified(category=ASK_PRICE)
  → FlowEventListener：找到 WAITING@n2 的实例 → 取消定时器 follow_up(SKIPPED)
  → advance(instance, event): n2 出口 ASK_PRICE → n5 HumanTask(QUOTE, escalate 2h)
       → 绑定已存在的审核单（同 lead 同类型 PENDING 则复用，不重复建）→ follow_up(due=now+2h, node=n5) → WAITING
  → 销售 1h 内批准发送 → 事件 ApprovalDone → advance: n5 出口 DONE → n2b GoTo(n2, loops=1/2)
       → n2 WaitForReply → 新定时器 72h → WAITING

若 72h 无回复 → FollowUpScheduler 到期 → advance(TIMEOUT): n2 出口 NO_REPLY → n3 Send(案例) → n3w Wait…
若客户回复"别发了" → 拒绝词 → BlacklistService → 实例 TERMINATED（不经过节点出口）
若销售在会话工作台"人工接管" → 实例 PAUSED；"交还机器" → RESUMED（若定时器已过期则立即按 TIMEOUT 推进）
```

## 7. 调度、队列与并发模型

| 关注点 | 方案 |
|--------|------|
| 定时任务 | **XXL-Job**（平台若已用 Quartz/Spring Scheduler 则改为对应实现）；每个 AutomationJob 映射一个带参任务；任务运行写 `job_run` |
| 发送队列 | Redis List/Stream，**按渠道账号分队列**（`acq:send:{accountId}`），每账号一个消费者串行执行，天然保证"一号一线" |
| 限流 | Redis 令牌桶（每账号：每小时、每日；每商家：每日总量）；活跃时段（默认 08:30–21:30）；新账号养号曲线（第 1–3 天 20%、4–7 天 50%、之后 100% 配额） |
| 随机延迟 | 由 `RiskGuard` 在 [min, max] 内按正态分布采样，下发到 `pacing`；同账号连续两条消息间隔 ≥ 配置值 |
| 去重 | 抓取原文 `raw_hash`（SHA-256(platform+contentId+authorId+text)）Redis Set 7 天 + DB 唯一索引 |
| 幂等 | 指令 `cmdId`、outreach 唯一键 (lead_id, script_id, job_run_id)、流程实例 `step_seq` 单调递增 + 行级锁 |
| 流程事件 | 入站分类 / 扫码 / 阶段变化 / 审核完成 / 人工任务完成 统一发布到内部事件总线（Spring Event 或 MQ），`FlowEventListener` 消费；事件带 `leadId` 路由到 WAITING 实例 |
| 长连接 | 执行端网关可独立部署多实例，`deviceId → 节点` 映射存 Redis，跨节点下发走 Redis Pub/Sub |
| 事务 | 线索建立/状态变更与事件写入同事务；外部发送不在事务内，回执异步更新 |
| 进度推送 | 任务运行进度通过 SSE 推给前端（复用海报系统 SSE 模式） |

## 9. 部署架构

```
                 ┌─────────── K8s / 虚机 ───────────┐
Nginx ──▶ hdz-app（含 hdz-ai-acquisition 业务节点 ×N）
     └──▶ acquisition-executor-gateway（WebSocket 长连接节点 ×2，独立扩缩）
          forum-worker（Playwright 浏览器自动化，独立进程/容器）
          XXL-Job Admin + Executor
     MySQL（主从）  Redis（哨兵/集群）  RocketMQ（可选）  OSS
                 └──────────────────────────────────┘
                          ▲ WebSocket (TLS)
   商家侧：工作手机 / 云手机（获客助手 App）×N  ——  一机一微信号
```

- 执行端网关与业务节点分离，避免长连接影响 REST 服务扩缩。

- 云手机方案下，商家不需要实体设备，由平台统一采购并按席位分配（可作为增值服务）。

## 10. 安全设计

| 项 | 方案 |
|----|------|
| 租户隔离 | 所有表带 `merchant_id`；MyBatis-Plus 多租户插件自动注入；销售仅可见 `owner_user_id=自己` 或主管授权范围 |
| 鉴权 | 复用平台 SSO / Token；权限编码 `acquisition:lead:view` 等（见 07 分册） |
| 执行端认证 | 设备绑定时颁发设备令牌（JWT，绑定 merchant/device），WebSocket 握手校验；令牌可吊销 |
| 敏感数据 | 手机号/微信号加密存储（AES）+ 展示脱敏；抓取原文不含手机号（正则剔除） |
| 审计 | lead_event 追加不可改；出站消息全量留存；人工操作记 operator |
| 密钥 | 企微 secret、模型 key 走平台配置中心，不落库明文 |
| 限流防刷 | 商家级日配额；平台级"总闸"可一键暂停所有 RPA 指令 |
| 数据保留 | 抓取原文 90 天、截图 30 天、消息 1 年（可按商家配置），到期自动清理 |
