> 项目：货袋子（huodaizi.com）  
> 模块：AI 货袋子获客系统（简称 **AI 获客**，模块代号 `hdz-ai-acquisition`）  
> 版本：v0.1（分析与架构设计稿，待确认后进入原型与开发）  
> 日期：2026-09-25

## 0. 一页结论

**AI 获客做的事，一句话：把"人在各平台找客户 → 一对一发消息 → 盯着回复 → 手工记表"这条链路，变成"系统抓意图线索 → 个性化触达 → 关键词/AI 自动跟进 → 自动记录与看板"的闭环，销售只处理高意向客户和复杂问题。**

本方案的核心设计决策（详见各分册）：

| # | 决策 | 结论 | 理由 |
|---|------|------|------|
| 1 | 模块形态 | 独立 Maven 子模块 `hdz-ai-acquisition`（包 `com.hdz.acquisition`，表前缀 `hdz_acq_`），前端为货袋子运营后台/商家后台中的独立路由模块 `/acquisition/*` | 与已有 `hdz-advertisement`、`hdz-leads`、`hdz-circle` 模块保持同一集成方式 |
| 2 | 多租户 | 以 **商家（merchant_id）** 为租户，销售（owner_user_id）为席位；平台按订阅收费 | 需求中"平台订阅费用"即 SaaS 模式，销售看板按人隔离 |
| 3 | 渠道分层 | **渠道抽象层 ChannelGateway + 适配器 SPI**。渠道按接入方式分三档：① 官方 API（企业微信客户联系、抖音开放平台、货袋子站内渠道）② HTTP/浏览器自动化（行业论坛、小红书网页版）③ **执行端 RPA**（个人微信、抖音 App、小红书 App，在工作手机/云手机上模拟真人操作） | 微信个人号、抖音、小红书都**没有**官方接口允许抓评论区/自动私信，只能靠 RPA；而 RPA 是封号高风险项，必须与官方渠道解耦、可单独开关 |
| 4 | 执行端 | 服务端（Java）只做"编排 + 排队 + 风控节流 + 下发指令"，真正在 App 里点击/输入/发送的是 **执行端（获客助手 App，Android 无障碍服务）**，通过 WebSocket 长连接收任务、回传结果和截图证据 | 服务端不持有微信登录态，风险隔离；小号先跑、稳定后上主号 |
| 5 | AI 用在四处 | ① 意图识别与打分（抓到的评论是不是"求推荐/怎么报名/有没有货"）② 个性化消息生成（带昵称、来源、历史互动，必须过变量校验）③ 回复匹配（**关键词规则优先，LLM 语义兜底**，命中话术库）④ 自然语言 → 定时任务 Spec 解析（"每天早上 9 点抓取线索"→ cron + 动作 + 参数，确认后生效） | 规则可控、可解释；LLM 只在规则未命中时兜底，且报价/合同/承诺效果一律转人工 |
| 6 | 复用已有能力 | 直接复用海报系统的 `poster_session / poster_share`（分享即出渠道码）做海报分发与扫码归因；复用企业资料库 `knowledge_item` 做话术 RAG；复用 `ModelGateway` 做模型路由；沉淀的线索回流平台"线索中心" | 不重复建设，海报扫码回来的咨询自动成为线索 |
| 7 | 五张业务表 | 需求中的"线索表、触达表、话术库、跟进表、看板表"为**系统预置表**（`hdz_acq_lead / outreach / script / follow_up / stat_daily`），商家不建表，只做字段扩展（`ext_json`）与开通向导 | 需求描述的"第一小时建表"在 SaaS 里应变成"开通即用" |
| 8 | 风控与合规 | 三条硬约束：**频率上限 + 随机延迟 + 拟人化时段**由服务端统一节流；**每条消息必须含 ≥1 个个性化变量**，否则不允许发送；**一次触达无回复 ≤ N 次后停止**，用户表态拒绝即进黑名单。报价、合同、承诺效果进入**人工审核队列** | 对应"避坑指南"四条；同时满足《个人信息保护法》最小必要、《广告法》与平台规范 |

**MVP 建议范围（详见 07 分册）**：先跑通"企业微信 + 货袋子站内渠道 + 行业论坛"三类低风险渠道的完整四步闭环 + 看板 + 自然语言定时任务；个人微信/抖音/小红书 RPA 执行端作为第二阶段，先小号灰度。
